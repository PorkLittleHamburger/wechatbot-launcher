# Windows desktop shell (Tauri 2)

The Windows shell lives here. React/Vite is in `desktop/src`, Python management
is in `python/wechat_onebot/launcher`, and staging/build scripts are in `scripts`.

## Build inputs

- Windows x64, a stable Rust MSVC toolchain, MSVC C++ linker/libraries and Windows
  SDK (including `rc.exe`). The repository's `scripts/desktop_env.ps1` selects the
  existing/portable toolchain and keeps Cargo output and bundler tools under the
  configured `CARGO_TARGET_DIR`.
- Node/npm and the locked frontend dependencies; `desktop/dist` is generated by
  `npm run build`. Dev Vite must listen at `http://localhost:1420`.
- The checked-in `icons/icon.ico` and generated `resources/runtime/`, including
  `python/python.exe`, `src/wechat_onebot/launcher/supervisor.py`, and schema-1
  `VERSION_MANIFEST.json`. Generated runtime resources are ignored by Git.
- `resources/vc_redist.x64.exe`, staged from a pinned Microsoft-signed official
  payload by `scripts/stage_desktop_prerequisites.ps1`, is embedded by the NSIS hook.
- Initial Cargo/NSIS/WebView2 dependency caching needs network access. The resulting
  NSIS installer embeds the offline WebView2 installer. `bundle.useLocalToolsDir`
  puts downloaded bundle tools inside Cargo's target directory. No signing is
  configured and there is no automatic release/publication step.

Configure tool paths as described in the [build guide](../../docs/building.md),
then set `WECHAT_RUNTIME_SOURCE` and run `scripts/build_desktop.ps1` from the repository root. For an
already staged runtime, the native build can also be invoked with
`npm.cmd run tauri -- build --bundles nsis` from `desktop`.

Release embeds `windows/app.manifest` with `requireAdministrator`. Debug embeds
`windows/debug.manifest` with `asInvoker`. Both are GUI-subsystem executables.
The product is **WeChat OneBot Launcher 0.8.5**; the binary is
`wechat-onebot-launcher.exe`; the application identifier is
`com.porklittlehamburger.wechat-onebot-launcher`.

## Supervisor lifecycle

Setup starts one process using the bundled interpreter:

```text
runtime/python/python.exe -B -u -m wechat_onebot.launcher.supervisor
  --root <workspace> --project <resource_dir>/runtime
```

`PYTHONDONTWRITEBYTECODE=1`, `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` are
explicitly passed in a Unicode environment block. Runtime resources are never
used for logs or settings. Stderr appends to `<workspace>/logs/supervisor.stderr.log`
(rotated on next start after 10 MiB); stdout is reserved for JSON lines.

The process is created hidden and suspended with a restricted inherited-handle
list, assigned to a private kill-on-close Job Object, and only then resumed.
Its descendants inherit job membership. Existing WeChat processes are never
opened, assigned, or terminated by this code. Failure to create/assign the job
fails startup rather than running an uncontained supervisor.

Requests are `{id,method,params}`. A mutex serializes stdin writes, while a map of
oneshot senders routes `{id,result}` / `{id,error:string}` responses by numeric ID.
Readiness waits for `ready` for up to **180 seconds**, including initial version
copying. Requests wait for readiness automatically. RPC responses have a 15-minute
deadline (version download/import can take time); a timeout does **not** imply
the Python operation was cancelled. Requests and responses are capped at 1 MiB,
with at most 256 pending requests.

Only `ready`, `operation-progress`, and `fatal` events are forwarded, to `main`
only; their event payload is the backend `data` value. Fatal/EOF rejects pending
requests. Startup failure is retained for later RPC callers and shown in main.

Exit is guarded against duplicate callers. It requests `shutdown` (8-second
response deadline, plus a bounded write), closes stdin, waits up to 22 seconds,
then terminates/drops only the owned job. Concurrent shutdown callers wait for
the same cleanup to finish. Power loss/OS termination can still interrupt writes.

## Frontend command contract and permissions

Only the local `main` window has a capability. Every custom command additionally
checks its window label and local origin. No `instance-*` window, remote origin,
wildcard window, or remote WebUI receives native permissions.

```ts
invoke('rpc', { method: 'snapshot', params: {} }) // resolves backend result
invoke('open_instance', { instanceId: '<32 lowercase hex characters>' })
invoke('reveal_workspace') // fixed workspace; accepts no arbitrary path
invoke('change_workspace', { path: 'D:\\Data\\WeChatOneBot' }) // absolute path
invoke('exit_app')
```

`open_instance` requests `instance_info` with `{id}` and requires a running row
with the same ID and a `http://127.0.0.1:<port>/...` URL. It opens/focuses
`instance-<id>`, restricts navigation to that origin, and grants no capability.
This is a native-IPC boundary; it does not claim a lower Windows integrity level
for WebView2 than the main app. A user can copy the URL into a normal browser.

The main capability grants only the five custom commands, event listen/unlisten,
and `dialog:allow-open` for the frontend file chooser. Opener and window-state
plugins are called from Rust without granting their JavaScript APIs.

The main close button uses `<workspace>/settings.json` `close_to_tray` (default
true). Tray Show and a second launch show/focus the existing main window. The
single-instance plugin applies to the desktop application, including QA workspaces:
stop an existing copy before testing a second workspace. Window-state saves only
main geometry/state, excluding visibility, so it cannot override autostart hiding.

`--workspace PATH` chooses an isolated root (otherwise the saved data-directory
preference or `%LOCALAPPDATA%/WeChatOneBotLauncher`). `--autostart` hides main only when
`autostart_hidden` is true; its default is false, matching the Python defaults.

`change_workspace` accepts only an absolute path from the main window. It rejects
the switch while any instance is active, removes the old autostart task, saves
the preference outside the workspace, shuts down the supervisor, and restarts
the app. Existing files are not migrated automatically.

## Settings and installer behavior

`rpc('settings_set', params)` is serialized in Rust. After Python accepts the
settings, changing `autostart` configures a current-user logon scheduled task via
`schtasks` XML: `InteractiveToken`, `HighestAvailable`, fixed executable, and
`--autostart --workspace <root>`. Task names include the current SID and a stable
workspace hash. An existing task must match this application's Source, user SID,
and executable before replacement/deletion. No legacy service task is touched.
Task changes preserve/restore prior task XML on failure; Python settings are
rolled back if task configuration fails. Any rollback failure is reported too.
No task is registered merely by building or starting the app.

NSIS installs per-machine in Simplified Chinese. Hooks replace Tauri's stock
force-kill macro with an exact-file Restart Manager check and manual
Retry/Cancel prompt. Silent installs abort if the launcher is running. Hooks do
not call force-shutdown or kill an existing process.

From 0.8.5, the update helper waits for exit, verifies SHA-256, and runs NSIS
with `/S /UPDATE /D=<current install directory>` (the unquoted `/D` is last).
It restarts the same executable with the original workspace after success or
recoverable failure. Exit timeout leaves the existing process alone. The helper
uses .NET hashing and supports the system Windows PowerShell without extra modules.

Uninstall disables/removes only tasks marked with this application's Source and
whose action points at this installation. In-place upgrades preserve those tasks.
It preserves data by default, including
unattended uninstall and upgrades. An explicit Yes prompt can remove only the
current user's standard workspace; redirected roots and any linked/junction
children are refused. QA/custom workspaces and other users' data are preserved.
When using alternate administrator credentials, Windows resolves current-user
settings/data to that elevated account; uninstall does not infer another user's
profile or remove its data.

## Validation boundaries

Use offline Mock backends for shell QA. UAC prompts, Task Scheduler behavior,
NSIS flows and tray interactions require separate Windows desktop acceptance.
Real WeChat bridging is validated separately. See the
[acceptance guide](../../docs/desktop-verification.md) for the procedure.
