# 代码审查：防御性编程与模块边界

日期：2026-11-04。原审查基线 `b7b5137`（v0.8.7 业务代码）。以下问题保留为原始审查证据，修复状态见下表；不能将原始行号套用到重构后的文件。

## 未发布：桥接恢复专项复查

在 v0.8.8 后的源码改动中独立复现并修复两项问题：

- P1：恢复 worker 异常退出后残留 `resume_requested`，升级健康检查可能继承该意图。现由每次 `_start_locked(..., resume_bridge=False)` 显式决定参数，升级/重启默认不恢复，退出时同步清理状态；真实 Mock 子进程崩溃后升级的命令捕获回归通过。
- P2：同一进程并发轮询的旧响应可能覆盖较新的停止状态。现按每实例轮询序号和进程身份共同判断提交资格；挂起旧等待响应、先提交新停止响应、最后释放旧响应的回归通过。

二次 CR 确认两项已解决，关联的旧 worker、错误分离、等待登录/取消和重启路径未发现新的可确认缺陷。验证只使用临时工作空间和 Mock/fake Runtime，不包含真实注入、发送或 Windows 注销登录。完整证据见[验收指南](desktop-verification.md)。

## 修复状态（启动器 0.8.8）

| 问题 | 当前实现及验证 |
| --- | --- |
| 下载阻塞停止 | Dispatcher 不再持全局变更锁；网络下载不占版本库锁，发布、创建、恢复、升级、删除由资源锁协调。异步流挂起下载时，创建和停止仍可完成；等待发布锁后会重新检查引用 |
| 创建半成品 | `instance_storage.py` 在临时目录写齐配置、版本与清单，一次重命名发布；配置写入、清单写入、发布失败均无残留实例 |
| 损坏归档阻断快照 | `CatalogReader` 返回带 `invalid/error` 的损坏条目；分区读取失败返回显式 `diagnostics`。界面区分故障与空列表，原生壳拒绝以失败的实例列表执行目录切换/安装更新 |
| 非对象参数被兜底 | 仅将 None 转为空字典，空列表、False、0、空字符串均拒绝，且不改写设置 |

维护性建议已落实到相应模块：前端页面与共享轮询/反馈 hooks 分离；恢复和回滚由 `RestoreService` 负责；通用取消安全线程执行移至 `async_utils.py`；RPC 使用单次结构化 DTO 校验；`autostart.rs` 统一自启事务，`scheduler.rs` 仅做系统适配。DesktopManager 仍作为应用协调器继承生命周期能力，不为拆分而增加通用框架。

复查还补齐：缺失实例清单或目录不再视为空列表；加密/不支持压缩格式的备份显示明确错误；重复取消不会提前释放文件线程持有的锁；目录切换与设置保存共用原生事务锁。

反馈新增按操作/资源归属的开始、进度、成功、失败和取消状态。每次操作另有独立关联 ID，迟到的旧批次事件不会污染重试结果。后端成功事件不代表 Windows 事务已完成，界面等待完整 RPC 确认；失败保留设置草稿，损坏备份/归档禁止恢复。实际微信操作、真实桌面安装/注销登录不在本次验证范围。

## 可复现问题

### P2：全局变更锁阻塞无关实例停止

位置：`python/wechat_onebot/launcher/supervisor.py:57`、`:94`。`Dispatcher.mutations` 同时包住运行包下载、备份和实例启停。界面允许运行实例时下载版本；下载期间发起停止请求，必须等待下载退出全局锁。测试以 Event 挂起下载，确认 stop 回调直到下载释放才执行。

建议：由应用操作服务管理每实例锁、版本库写锁和必要的跨资源事务。网络下载放在版本发布锁之外，校验及发布阶段再锁定共享状态；保留删除版本与实例引用检查的原子性。不能简单删除全局锁而失去当前隐含的互斥保证。

### P2：跨继承层的创建事务留下半成品

位置：`python/wechat_onebot/launcher/desktop_manager.py:91`。`super().create` 先发布实例目录和清单，子类随后 `_bind_version` 并重写带版本的清单。绑定失败时没有清理基类已创建的目录。隔离测试模拟绑定时 `OSError`，调用失败后 `rows()` 仍返回一条没有 `version` 的实例，后续启动无法解析运行版本。

建议：用独立创建服务统一组装配置、版本及清单，在临时目录完成后一次发布；所有失败路径都由同一事务所有者清理。避免把一个必须原子的操作拆成父类先提交、子类再补字段。

### P2：单一归档损坏使整个快照不可用

位置：`python/wechat_onebot/launcher/desktop_manager.py:178`、`:298`。`snapshot()` 同步串联实例、版本、备份、归档与设置读取；`archives()` 的 JSON 解析异常直接向上传播。隔离测试只在一个归档中写入损坏 JSON，实例列表仍可读取，但 snapshot 整体失败。前端每两秒重复请求该快照，无法更新其他正常模块。

建议：分离目录读取服务，给损坏条目明确的状态和诊断，或在快照中提供各模块的错误结果；不要使用顶层 `except: return []` 把损坏伪装为空列表。恢复和变更操作仍需严格验证被操作对象。

### P3：宽泛空值兜底绕过参数类型校验

位置：`python/wechat_onebot/launcher/supervisor.py:22`。`params = params or {}` 在类型检查前把 `[]`、`False`、`0`、空字符串变成字典。隔离测试向 `settings_set` 传入 `[]`，得到正常设置结果而非协议错误。桌面 Rust 当前会先检查参数为对象，因此影响主要在 Python IPC 的独立契约和测试/未来调用方。

建议：仅对明确支持的 `None` 使用空字典，其余错误类型直接拒绝；用表驱动测试覆盖 None、对象及上述非法值。

## 维护性建议（不计为已复现功能缺陷）

- `desktop/src/App.tsx` 同时持有五个页面、轮询、操作锁、日志、更新、设置及模态状态。按功能提取页面和 hooks，保留一个共享快照/操作协调入口，避免每页重新建立轮询和锁。
- `DesktopManager` 同时负责持久化、进程、版本绑定、端口检查、备份恢复和升级事务。逐步采用组合，将生命周期、目录仓储、备份与升级操作分开；先定义失败语义再移动文件。
- 备份恢复多次调用 `VersionStore._thread`，取消安全的线程执行本不属于版本库私有职责。应放入共享异步工具，保留“等待线程实际结束再释放锁”的行为。
- `desktop/src/api.ts` 对 RPC 返回字符串再做 `JSON.parse`，但当前 Rust RPC 返回 `serde_json::Value`，没有已支持的双重编码协议。建议移除无依据的兼容分支，统一 DTO；这是维护性问题，本次没有发现正常 RPC 结果被误解析的现存触发路径。
- `scheduler.rs` 内外层分别查询任务、解析 SID、验证所有权和回滚任务，增加事务推理成本。由一个协调器持有任务/注册表快照，底层只做系统读写；迁移时保持所有权检查与失败回滚能力。

## 应保留的检查与建议顺序

跨盘相对路径失败后改为绝对路径、Windows 路径身份检查、归档越界检查、取消后的线程等待、启动探测重试、React 卸载后更新保护，以及异常清理后重新抛出，都有明确用途，不应以“精简判空”批量删除。

优先处理创建事务与快照故障隔离，再重划锁域并补并发回归；参数兜底可以独立修复。随后提取前端功能和后端服务，每一步保持行为、错误和取消语义可验证。原始建议的落实情况以上方修复状态为准；后续修改仍需覆盖锁、取消、发布及回滚边界。
